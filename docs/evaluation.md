# KITTI Road의 FP32·INT8 비교

62장의 주행 분리 평가 집합에서 INT8 변환 후 도로 IoU는 77.331%에서 77.547%로 변했다. 두 모델의 판정이 달라진 픽셀은 유효 픽셀 756,556개 중 1,464개였다. 같은 단일 스레드 CPU에서 INT8의 순수 추론 지연시간 중앙값은 0.427ms로, FP32의 0.971ms보다 56.0% 짧았다. [측정 요약](../artifacts/benchmark.json) · [장면별 원시 결과](../artifacts/scene_metrics.csv) · [호출별 시간](../artifacts/latency.csv)

| 측정 항목 | FP32 TFLite | INT8 TFLite |
|---|---:|---:|
| 유효 영역 도로 IoU | 77.331% | 77.547% |
| 유효 영역 픽셀 정확도 | 95.207% | 95.242% |
| invoke p50 / p95 | 0.971 / 1.108ms | 0.427 / 0.481ms |
| 정규화 RGB 입력 → 확률맵 p50 / p95 | 1.013 / 1.170ms | 0.490 / 0.569ms |
| TFLite 파일 크기 | 322,536B | 92,832B |
| 워밍업 직후 프로세스 RSS | 545.34MiB | 545.11MiB |
| 모델 로드 직전 대비 RSS 증가 | 7.03MiB | 5.41MiB |

INT8 모델은 FP32 파일 크기의 28.8%다. 전체 RSS에는 Python·TensorFlow·공유 라이브러리가 포함된다. Linux의 페이지 단위 RSS 스냅샷과 런타임 메모리 할당 시점 때문에 작은 프로세스 간 차이를 모델 메모리 절감률로 해석하기는 어렵다.

## 어떤 장면에서 결과가 달라졌나

| 조건 | 장면 수 | FP32 도로 IoU | INT8 도로 IoU |
|---|---:|---:|---:|
| 원본 · 표시 차선 도로 (UM) | 19 | 80.690% | 80.993% |
| 원본 · 다차선 도로 (UMM) | 21 | 79.881% | 80.308% |
| 원본 · 무표시 도로 (UU) | 22 | 71.011% | 70.891% |
| 원본 · 도로 면적 하위 25% | 16 | 72.317% | 72.081% |
| 합성 · 저조도 | 62 | 31.037% | 33.062% |
| 합성 · 중앙 가림 | 62 | 74.291% | 74.730% |

도로 면적은 유효 도로 픽셀 수를 전체 64×192 격자 크기로 나눈 값이다. 이를 오름차순 정렬한 첫 16장(최대 15.25%)은 앞의 세 도로 유형에 중복 포함된다. 이 16장의 INT8 IoU는 0.236%p 낮아졌고, 무표시 도로에서도 0.120%p 낮아졌다. 같은 원본으로 생성한 두 합성 조건은 각각 별도로 집계했다. 밝기를 RGB의 35%로 낮추거나, 화면 너비 3/8~5/8·높이 1/2~3/4의 사각형을 중성 회색 0.25로 덮었다. 가림 전의 정답을 유지해 센서 시야 손실 민감도를 측정했다. 실제 야간 촬영·물체 가림·소형 객체 성능을 판단하려면 해당 라벨을 갖춘 데이터가 필요하다.

- 원본 최저 INT8 IoU 장면인 `umm_000081`에서 모델이 앞차 뒤쪽의 좁은 차로만 도로로 표시했다. INT8이 정답 도로 2,756픽셀 중 1,972개를 놓쳐 IoU는 28.24%였다. FP32도 27.95%였다. 두 정밀도가 이 장면에서 서로 다르게 판정한 픽셀은 12개다. [원본](../web/scenes/umm_000081_clean_input.jpg) · [정답](../web/scenes/umm_000081_clean_truth.jpg) · [INT8](../web/scenes/umm_000081_clean_int8.jpg)
- `um_000028` 합성 저조도에서는 두 모델 모두 유효 영역 전체를 배경으로 판정했다. INT8이 놓친 도로 픽셀은 2,252개이며 FP32와 INT8의 서로 다른 판정은 0개였다. 이 장면은 양자화 전부터 존재한 밝기 민감성을 보여 준다. [합성 입력](../web/scenes/um_000028_dim_input.jpg) · [정답](../web/scenes/um_000028_dim_truth.jpg) · [INT8](../web/scenes/um_000028_dim_int8.jpg)

데모는 도로 유형별 INT8 IoU 중앙 순위 1장씩(짝수면 아래 순위), 원본 전체 최저 1장, 각 합성 조건 최저 1장을 고른다. 동점은 원본 ID 오름차순으로 결정한다. 이 선택은 대표적인 결과와 실패를 함께 검토하기 위한 규칙이다. 대표 수치는 전체 평가 픽셀에서 계산한다. 이미지는 카메라 원본 해상도를 유지하고, 유효 영역 내 64×192 정답과 예측을 최근접 보간해 같은 색으로 덧씌운다. KITTI 원본·가공 이미지의 출처는 A. Geiger, P. Lenz, C. Stiller, R. Urtasun 및 KITTI Vision Benchmark Suite이며, 가공 작업은 리사이즈된 마스크·합성 변형·JPG 인코딩이다. ## 재현과 해석

저장소 루트, Linux, 설치된 프로젝트 의존성 및 KITTI `data_road.zip`이 필요하다.

```bash
python -m src.bench --archive /path/to/data_road.zip --warmup 20 --repeats 10
python -m unittest discover -s tests -p test_runtime.py -v
python -m unittest discover -s tests -p test_bench.py -v
```

1. 공식 주행 ID로 분리한 학습 201장, 보정 26장, 홀드아웃 62장(7개 주행)을 사용했다. 각 영상은 RGB 64×192, 0~1 float32로 리사이즈했다. 마스크는 최근접 보간했다. 유효 영역은 원본 라벨의 적색 채널, 도로는 청색 채널을 사용했다. [분할 ID](../artifacts/split.json) · [전처리](../src/data.py)
2. 같은 평가 입력과 확률 임곗값 0.5를 사용했다. INT8 입력은 `clip(rint(x / scale) + zero_point, -128, 127)`, 출력은 `(q - zero_point) × scale`이다. 실제 파일의 입력 scale은 0.00392156886, 출력 scale은 0.00390625, 두 zero point는 −128이다. 유효 영역의 평균 절대 확률 차이는 0.002538이다. [런타임](../src/runtime.py)
3. 각 표에서 도로 IoU는 장면의 TP·FP·FN을 먼저 합산한 뒤 TP/(TP+FP+FN)으로 계산했다. 정확도는 정답인 유효 픽셀의 비율이다. 도로와 도로 예측이 모두 없는 장면의 단독 IoU는 미정의로 처리한다. 이 지표는 카메라 격자의 1개 클래스 도로 IoU다. 공식 KITTI 도로 벤치마크는 BEV 좌표계와 다른 지표를 사용한다. [KITTI 공식 평가](https://www.cvlibs.net/datasets/kitti/eval_road.php)
4. Linux x86_64 AMD EPYC 9V74, TensorFlow CPU 2.19.1 TFLite/XNNPACK, 스레드 1개, batch 1로 측정했다. 두 모델은 새 프로세스에서 차례대로 실행했다. 모형별 첫 평가 입력을 20회 워밍업한 후, 메모리에 올린 원본 62장을 매 회차 시드 731의 순열로 섞어 10회 반복했다. `latency.csv`는 모델마다 620개 측정치를 담는다. `invoke_ns`는 입력 복사 이후부터 출력 복사 전까지의 `invoke()` 시간이다. `frame_ns`에는 입력 검증·양자화·텐서 복사·출력 복원도 포함된다. 파일 읽기·리사이즈·마스크 렌더링은 두 타이머 바깥에 있다. p50/p95는 전체 호출 시간의 백분위수이며 가상 CPU 부하에 따라 달라질 수 있다. [평가 코드](../src/bench.py)
5. 인터프리터가 잘못된 파일·입출력 형식·유효 범위를 거부하는지 시험했다. 추론 오류가 발생한 프레임은 실패로 반환하고, 다음 유효 입력 때 인터프리터를 다시 생성한다. 단위 시험은 이 오류를 주입하고 복구를 확인한다. 별도 통합 시험에서 실제 손상 파일 거부 및 두 배포 모델의 입력 오류 후 동일 출력도 확인한다. [런타임 시험](../tests/test_runtime.py) · [평가식 시험](../tests/test_bench.py)

모델마다 CPU 위임 파티션 5개가 기록됐다. 장치별 NPU 실행 시간, 보드 전력, 실차 실시간성은 이 CPU 측정 범위를 벗어난다. 7개 주행에서 얻은 점 추정치이므로 소폭의 IoU 상승을 다른 환경의 개선으로 일반화하기 어렵다.
